# kuik acceptance scenarios of a release

## Overview

Prepares, once per release and before its acceptance run, the scenarios the [`release-acceptance`](../release-acceptance/SKILL.md) skill will run. A scenario is a user story in [`scenarios.md`](../../../test/acceptance/scenarios.md): what a user does, what they expect with its `docs/v3/` link, and the commands that prepare and check it, so a human could run it by hand. Its fixture lives under [`test/acceptance/fixtures/`](../../../test/acceptance/fixtures/) ([note 0015](../../../notes/0015-acceptance-tooling-acts-the-agent-judges.md)).

You draft; **the user decides** which scenarios exist. Nothing is written before they agree.

## Hard rules

- **No cluster**: never run an acceptance task other than `task acceptance-validate`, never run `kubectl` or `helm`. The scenarios are checked on a cluster by `release-acceptance`, after review.
- **The user validates every scenario** before you write it, and is always invited to add their own.
- **The spec is read-only**: never edit `docs/v3/`. A scenario that contradicts it is a question for the user, not a spec change.
- **Scenarios stay inside the guard**: test objects are those [the guard](../../../test/acceptance/README.md#the-guard) lets through. A new kind of test object extends the guard in `guard.go`, a reviewed code change you name to the user first.
- **Check commands only read**: `task acceptance-inspect` with `--grep` and `--metrics`, or `KUBECONFIG=<path> kubectl --context <name> get ... -o jsonpath=...`. Never a command that reads a Secret's data.
- **No push**: the work ends in local commits, handed to the [`pull-request`](../pull-request/SKILL.md) skill.

## Workflow

### 1. Inputs

1. The new version (for example `3.0.0-alpha.4`). Ask if it is missing.
2. The previous version: the latest `v3.*` tag before it (`git fetch --tags origin`, then `git tag --list 'v3.*' --sort=-v:refname`).
3. Work on a branch off a fresh `origin/main`, as the `pull-request` skill says.

### 2. What changed

There is no changelog file: the release notes are the GitHub release body, generated by semantic-release from the conventional commits ([`.releaserc.mjs`](../../../.releaserc.mjs)).

- When the tag exists: `gh release view v<version>` and `git log --oneline v<previous>..v<version>`.
- When it is not cut yet: `git log --oneline v<previous>..origin/main`.

Keep `feat`, `fix` and breaking changes; keep a `chore`, `docs` or `test` commit only when it changes what a user sees (a chart value, a metric). Open the pull request, the code at the tag or `docs/v3/` where a commit is unclear.

### 3. What a user can observe

For each change kept, write what a user does and sees on a cluster: a pod rewritten or not, a status field, a condition and its reason, an event, a metric, a log line, an injected Secret, a chart value. Drop what nothing on a cluster shows; the Kind e2e suite covers it.

Then read [`scenarios.md`](../../../test/acceptance/scenarios.md):

- a change that alters an existing scenario amends it (its expectation, its check); it does not duplicate it;
- a scenario the release makes obsolete is proposed for removal;
- a "scenarios to add" section of the last acceptance report, if the user has one, is input too.

### 4. Draft and ask

Show the draft as a numbered list, one scenario per item: **The user**, **They expect** (each point with its `docs/v3/` link) and the fixture it needs, in a few lines. Then ask the user, with AskUserQuestion or plain questions:

- which to keep, drop or change;
- **what they want checked on every release that is not in the list**: invite their own scenarios explicitly.

Iterate until the user agrees with the whole list. **STOP** at each round and wait for the answer.

### 5. Write

1. In `scenarios.md`, one section per scenario, numbered after the last one, with its fields in order: **Since** (the new version), **The user**, **They expect**, **Prepare**, **Do**, **Check**, **Explore**. Copy the shape of an existing section; amend the scenarios step 4 changed.
2. Each new fixture is `test/acceptance/fixtures/<NN>-<slug>.yaml`, `<NN>` the scenario number. Its first line is `# since: <version>`. It uses `${KUIK_NAMESPACE}` instead of the kuik namespace, and names its test objects `kuik-test-*`. A scenario that reuses a fixture names it in **Prepare** and adds none. `${PRIVATE_REPO}` and `${PULL_AUTH}` are set only on a run with a private repository, `${MIRROR_PREFIX}` only on a run with `--mirror-prefix`, and `setup` skips without them only the files its skip rules name (`11-` and `13-`, `14-`): any other fixture that uses them fails every run without one, and `acceptance-validate` cannot see it. A scenario that needs the private repository gets its own numbered fixture, so it keeps its own `since`, and extends the skip rule of `setup.go` (and the Scenarios paragraph of the README) to it: a change named to the user first. Never add it to the `11-` files, whose `since` is older.
3. A new kind of test object: extend `guard.go`, and the guard section of the [README](../../../test/acceptance/README.md#the-guard).
4. An ImageMirror fixture writes to a `.invalid` host. One that must copy for real needs `--mirror-prefix`, a registry path the user dedicates to the test on every run: name it to the user first. Credentials are `kuik-test-*` Secrets or `${PULL_AUTH}`, never another Secret.

### 6. Check

One task per Bash call, and fix what they report in your files:

1. `task acceptance-validate`: every fixture decodes, passes the guard and carries its `since` line. No cluster needed.
2. `task lint-markdown`.
3. `task lint`, when a Go file changed.

### 7. Hand over

Commit a change to the program (`guard.go`, a skip rule of `setup.go`, a new fixture variable, any Go file or the Taskfile) in its own commit, then the scenarios as `test(e2e): add the acceptance scenarios of <version>`. The branch can run on a cluster with the [`release-acceptance`](../release-acceptance/SKILL.md) skill before its pull request opens: fixtures and Markdown need no approval, a program change one `task acceptance-approve` for the whole run, after the agent explains it. Then hand over to the [`pull-request`](../pull-request/SKILL.md) skill.

## Common mistakes

| Mistake | Fix |
| ------- | --- |
| Writing the scenarios before the user agrees | Draft, ask, iterate; write only the agreed list |
| A scenario per commit | One per behaviour a user can observe; a refactor or a test change has none |
| A scenario only Kind can show | Drop it: the e2e suite covers it |
| Duplicating a scenario the release changes | Amend the existing one |
| An expectation without its spec link | Every point of **They expect** links its `docs/v3/` section |
| `${PRIVATE_REPO}` or `${PULL_AUTH}` in a fixture the skip rule of `setup.go` does not cover | Extend the skip rule to its own numbered fixture, after asking the user; never grow the `11-` files |
| A check that reads a Secret's data | Check its name, type, keys or owner, never its data |
| Running the scenarios to try them | Only `task acceptance-validate`; the cluster is `release-acceptance`'s job |
